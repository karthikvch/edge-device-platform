**Certificates and CA (development)**

This document describes the development Certificate Authority (CA) and the certificates generated by the `scripts/generate-certs.sh` script.

**What the script creates**
- `certs/ca/ca.key` — CA private key (keep secret).
- `certs/ca/ca.crt` — CA self-signed certificate (public trust anchor).
- `certs/server/server.key` — server private key.
- `certs/server/server.crt` — server certificate signed by the CA (for `localhost`).
- `certs/devices/dev-001/device.key` — device (client) private key for `dev-001`.
- `certs/devices/dev-001/device.crt` — device certificate signed by the CA.

**Purpose of the CA**
- The CA signs server and device certificates so clients and servers can verify each other's identity.
- Any system that trusts `ca.crt` will trust certificates signed by it.
- This CA is intended for development and testing only.

**Where files live**
- The script creates the certificates under the repository `certs/` tree. Run the script from the repo root to populate `certs/`.

**How to trust the CA (examples)**
- For a Linux client (system-wide, Debian/Ubuntu example):

```bash
sudo cp certs/ca/ca.crt /usr/local/share/ca-certificates/edp-dev-ca.crt
sudo update-ca-certificates
```

- For a single process (e.g., a Python TLS client) point to the CA bundle when creating the TLS context. Example (OpenSSL CLI):

```bash
openssl s_client -connect localhost:8883 -CAfile certs/ca/ca.crt
```

- For Mosquitto broker, set `cafile` in the config to `certs/ca/ca.crt` and use `keyfile`/`certfile` for server cert.

**Inspecting certificates**

```bash
openssl x509 -in certs/server/server.crt -noout -text
openssl x509 -in certs/devices/dev-001/device.crt -noout -text
openssl x509 -in certs/ca/ca.crt -noout -text
```

**Verify server cert chain**

```bash
openssl verify -CAfile certs/ca/ca.crt certs/server/server.crt
```

**Security notes**
- `certs/ca/ca.key` is the private CA key — treat it like any private key and do not commit it to public repositories.
- If `ca.key` is leaked, all signed certs are untrusted and must be reissued using a new CA.
- For production, use a professionally-managed CA or PKI with proper key storage (HSM/secure vault) and revocation.

**Renewal / validity**
- Certificates in this script are generated with 365 days validity. To renew, re-run the script (or create new CSRs and sign them using the CA).

**Extending for more devices**
- Copy `certs/devices/dev-001/` structure and run OpenSSL commands similar to the script, changing the CN for each device.

**Example: manually create and sign a device cert**

```bash
# generate key
openssl genrsa -out certs/devices/dev-002/device.key 2048
# create CSR
openssl req -new -key certs/devices/dev-002/device.key -out certs/devices/dev-002/device.csr -subj "/CN=dev-002"
# sign with CA
cat > certs/devices/dev-002/device.ext <<EOF
extendedKeyUsage=clientAuth
EOF
openssl x509 -req -in certs/devices/dev-002/device.csr -CA certs/ca/ca.crt -CAkey certs/ca/ca.key -CAcreateserial -out certs/devices/dev-002/device.crt -days 365 -sha256 -extfile certs/devices/dev-002/device.ext
```

**How the project uses these certs (notes)**
- The `backend` and `agent` components can be configured to use these certificates for TLS-secured MQTT and other connections. Check the broker and client configuration files to point to `certs/server/*` and `certs/ca/ca.crt`.

**Script location**
- See `scripts/generate-certs.sh` for the exact commands used to generate these files.

**Production CA (recommendations)**

- **Separate from dev CA:** Use a dedicated production CA; do not reuse the development CA created by `scripts/generate-certs.sh`.
- **Root / intermediate model:** Use a highly-protected offline root CA and one or more online intermediate CAs that actually issue certificates. Keep the root CA offline.
- **Secure key storage:** Store CA private keys in an HSM or secure key-vault (e.g., AWS KMS, Azure Key Vault, HashiCorp Vault) with strict access controls and auditing.
- **Automated issuance & rotation:** Use a certificate management system (or ACME-based tooling where appropriate) to automate issuance, renewal, and rotation; prefer short-lived certificates.
- **Revocation & validation:** Implement revocation checking (OCSP/CRL) or use short-lived certs so revocation requirements are minimized; ensure clients validate revocation status when necessary.
- **Policy & auditing:** Enforce issuance policies (subject rules, SAN constraints, key sizes, EKU), log all issuance actions, and audit access to CA operations.
- **Monitoring & incident response:** Monitor for suspicious activity and have a plan to revoke and reissue certificates if a CA key is compromised.
- **Use established PKI:** For production, consider managed PKI providers or enterprise PKI solutions rather than ad-hoc OpenSSL scripts.
